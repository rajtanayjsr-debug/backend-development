# Assignment 2 — PostgreSQL as SQL + NoSQL: Working with JSONB

## Learning Objective

The objective of this assignment is to understand how PostgreSQL's `jsonb` data type allows a relational database to support both structured SQL data and flexible document-style NoSQL data. It also explores how PostgreSQL with JSONB can be used as an alternative to MongoDB in suitable applications.

---

# Part A — Conceptual Questions

## Question 1: What is `jsonb` in PostgreSQL, and how does it differ from the plain `json` type?

PostgreSQL provides two data types for storing JSON data: `json` and `jsonb`. Both allow us to store JSON documents inside a PostgreSQL database, but they store and process the data differently.

The `json` type stores the data as its original text. Because PostgreSQL does not need to convert the input into another format, inserting data can be slightly faster. However, whenever the data is queried, PostgreSQL must process the JSON text again.

The `jsonb` type stores JSON data in a decomposed binary format. It may require slightly more processing while inserting data, but querying is generally faster because the data has already been processed. Another major advantage of `jsonb` is that it supports indexing, such as GIN indexes, which can significantly improve search performance.

For example:

```sql
CREATE TABLE products (
    id SERIAL PRIMARY KEY,
    details JSONB
);

INSERT INTO products (details)
VALUES ('{"name": "Laptop", "brand": "Dell", "ram": "16GB"}');

SELECT details->>'name' AS product_name
FROM products;

## Question 2: How can PostgreSQL work as both a SQL and a NoSQL database in the same table?

PostgreSQL can support both SQL and NoSQL-style data in the same table by combining normal relational columns with a `jsonb` column. The relational columns are useful for data that has a fixed structure, while the `jsonb` column can store flexible attributes that may differ between records.

For example, an e-commerce system may store common product information such as ID, name, and price in regular SQL columns. Different products may have different properties, such as RAM for a laptop or size for clothing. These variable properties can be stored inside a `jsonb` column.

```sql
CREATE TABLE products (
    id SERIAL PRIMARY KEY,
    name VARCHAR(100) NOT NULL,
    price DECIMAL(10,2),
    attributes JSONB
);
```

Example data can be inserted as:

```sql
INSERT INTO products (name, price, attributes)
VALUES (
    'Laptop',
    75000.00,
    '{"brand": "Dell", "ram": "16GB", "storage": "512GB SSD"}'
);
```

Here, `id`, `name`, and `price` follow a fixed relational schema, while `attributes` behaves like a flexible JSON document. We can still use normal SQL queries together with JSONB operators.

```sql
SELECT name, attributes->>'ram' AS ram
FROM products;
```

Therefore, PostgreSQL provides the reliability and structure of a relational SQL database while also supporting flexible document-style data similar to a NoSQL database.

## Question 3: Give an example of a `jsonb` query using `->`, `->>`, `@>`, and `?`.

PostgreSQL provides several operators for accessing and searching data stored in a `jsonb` column. Suppose a product contains the following attributes:

```json
{"brand": "Dell", "ram_gb": 16, "wireless": true}
```

The `->` operator retrieves a value as JSON:

```sql
SELECT '{"brand": "Dell", "ram_gb": 16}'::jsonb -> 'brand';
```

Returned value:

```text
"Dell"
```

The `->>` operator retrieves the value as SQL text:

```sql
SELECT '{"brand": "Dell", "ram_gb": 16}'::jsonb ->> 'brand';
```

Returned value:

```text
Dell
```

Therefore, `->` returns a JSON/JSONB value, whereas `->>` returns the extracted value as text. This makes `->>` useful when a value needs to be displayed, compared, or converted to another SQL data type.

The `@>` operator checks whether one JSONB value contains another:

```sql
SELECT '{"brand": "Dell", "wireless": true}'::jsonb
       @> '{"wireless": true}'::jsonb;
```

Returned value:

```text
true
```

The `?` operator checks whether a specified key exists in a JSONB object:

```sql
SELECT '{"brand": "Dell", "ram_gb": 16}'::jsonb ? 'ram_gb';
```

Returned value:

```text
true
```

Thus, these operators allow PostgreSQL to extract JSON values, retrieve them as text, test containment, and check for the existence of keys.

## Question 4: How can a GIN index on a `jsonb` column change query performance?

A GIN (Generalized Inverted Index) index can significantly improve the performance of queries that search inside a `jsonb` column. Without an index, PostgreSQL may need to perform a sequential scan, which means checking every row in the table to determine whether its JSONB data matches the condition. This can become slow when a table contains thousands or millions of records.

For example, an index can be created on the `attributes` column as follows:

```sql
CREATE INDEX idx_products_attributes
ON products USING GIN (attributes);
```

This index is particularly useful for JSONB containment queries using the `@>` operator. For example:

```sql
SELECT name
FROM products
WHERE attributes @> '{"wireless": true}';
```

With a suitable GIN index, PostgreSQL can locate matching JSONB values without scanning the entire table.

However, a standard GIN index on the complete JSONB column does not automatically improve every type of query. For example:

```sql
SELECT *
FROM products
WHERE price > 1000;
```

This query filters the normal `price` column rather than the JSONB `attributes` column, so the JSONB GIN index does not help it. A separate index on `price` would be required if this query needed optimization.

Therefore, GIN indexes are especially useful for containment and key-search operations on JSONB data, but appropriate indexes must be selected according to the queries being executed.

## Question 5: Where could PostgreSQL + `jsonb` replace a MongoDB deployment, and where would MongoDB still be the better fit?

PostgreSQL with `jsonb` can replace MongoDB in applications that require both structured relational data and flexible document-style data. PostgreSQL is especially suitable when an application needs strong transactions, relationships between tables, joins, and schema enforcement while also storing some attributes whose structure may vary.

For example, an e-commerce application can store important product information such as `id`, `name`, and `price` in typed columns while keeping category-specific information in a `jsonb` column.

```sql
SELECT p.name, o.quantity
FROM products p
JOIN order_items o ON p.id = o.product_id
WHERE p.attributes @> '{"wireless": true}';
```

PostgreSQL provides ACID transactions and powerful SQL joins, making it useful for systems such as e-commerce, banking, inventory, and business applications where data consistency and relationships are important. It also allows schema enforcement through data types and constraints.

MongoDB may still be a better choice for applications built primarily around flexible documents with rapidly changing structures. Its document model can be simpler when most data naturally belongs in nested documents rather than related tables. MongoDB also provides built-in approaches for distributing data across multiple servers through sharding, which can make horizontal scaling convenient for very large document-oriented workloads.

Therefore, PostgreSQL with `jsonb` is a strong choice when relational and document features are both required, while MongoDB can be preferable for highly document-oriented systems where flexible structures and large-scale horizontal distribution are major requirements.

# Part B — Hands-on Exercise: Product Catalog

## Task 1 — Schema

The following table combines fixed relational columns with a flexible `jsonb` column called `attributes`. The fixed columns maintain a consistent structure, while `attributes` can store different information for different product categories.

```sql
CREATE TABLE products (
    id INTEGER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    name VARCHAR(100) NOT NULL,
    category VARCHAR(50) NOT NULL,
    price NUMERIC(10,2) NOT NULL,
    attributes JSONB
);
```

The `id`, `name`, `category`, and `price` columns follow a fixed relational schema. The `attributes` column allows each product category to store its own category-specific properties without changing the table structure.

## Task 2 — Insert Data

Five products are inserted across three different categories: `book`, `laptop`, and `accessory`. Each category uses different keys inside the `attributes` JSONB column.

```sql
INSERT INTO products (name, category, price, attributes) VALUES
('Clean Code', 'book', 499.00,
 '{"author": "Robert C. Martin", "pages": 464}'),

('Atomic Habits', 'book', 399.00,
 '{"author": "James Clear", "pages": 320}'),

('Dell Inspiron', 'laptop', 65000.00,
 '{"ram_gb": 16, "cpu": "Intel Core i5", "storage_gb": 512}'),

('HP Pavilion', 'laptop', 78000.00,
 '{"ram_gb": 16, "cpu": "Intel Core i7", "storage_gb": 1024}'),

('Wireless Mouse', 'accessory', 1299.00,
 '{"color": "Black", "wireless": true}');
```

Here, books contain attributes such as `author` and `pages`, laptops contain `ram_gb`, `cpu`, and `storage_gb`, while the accessory contains `color` and `wireless`. This demonstrates how JSONB can store different structures in the same column.

## Task 3 — Query by Category-Specific Attribute

The following queries demonstrate how JSONB attributes can be used to filter products based on properties specific to each category.

### 1. Book Query — Find books with more than 400 pages

```sql
SELECT name, attributes ->> 'author' AS author
FROM products
WHERE category = 'book'
  AND (attributes ->> 'pages')::int > 400;
```

This query uses the `pages` attribute, which is specific to books. It returns `Clean Code` because it has 464 pages.

### 2. Laptop Query — Find laptops with at least 16 GB RAM

```sql
SELECT name, attributes ->> 'cpu' AS cpu
FROM products
WHERE category = 'laptop'
  AND (attributes ->> 'ram_gb')::int >= 16;
```

This query filters laptops using the `ram_gb` JSONB attribute. It returns both `Dell Inspiron` and `HP Pavilion` because both have 16 GB RAM.

### 3. Accessory Query — Find wireless accessories

```sql
SELECT name, attributes ->> 'color' AS color
FROM products
WHERE category = 'accessory'
  AND (attributes ->> 'wireless')::boolean = true;
```

This query uses the `wireless` attribute specific to accessories. It returns `Wireless Mouse`, whose `wireless` value is `true`.

These queries show that different product categories can be searched using their own attributes even though all of those attributes are stored in the same JSONB column.

## Task 4 — Containment Query

The `@>` operator checks whether a JSONB value contains a specified JSON structure.

The following query finds products where the `attributes` column contains `"wireless": true`:

```sql
SELECT name
FROM products
WHERE attributes @> '{"wireless": true}';
```

### Expected Result

```text
Wireless Mouse
```

The query searches inside the JSONB `attributes` column and returns the `Wireless Mouse` because its attributes contain:

```json
{
  "color": "Black",
  "wireless": true
}
```

The `@>` containment operator is useful when we want to search JSONB documents for a particular key-value pair without knowing or checking the other attributes stored in the document.

## Task 5 — Update JSONB Without Altering the Table

One advantage of JSONB is that new attributes can be added without changing the structure of the database table.

The following query adds a `discount_pct` attribute to the existing `Wireless Mouse` product:

```sql
UPDATE products
SET attributes = attributes || '{"discount_pct": 10}'
WHERE name = 'Wireless Mouse';
```

To verify the update:

```sql
SELECT name, attributes
FROM products
WHERE name = 'Wireless Mouse';
```

### Expected Result

```text
Wireless Mouse | {"color": "Black", "wireless": true, "discount_pct": 10}
```

The `||` operator merges the existing JSONB object with the new JSONB value. Therefore, `discount_pct` is added to the product without using an `ALTER TABLE` command or creating a new database column.

This demonstrates the flexibility of JSONB for storing attributes that may change or differ between products.

## Task 6 — Index and Compare

A GIN index can be created on the `attributes` JSONB column to improve the performance of JSONB containment queries.

### Query Before Creating the Index

First, the query can be analyzed without the GIN index:

```sql
EXPLAIN ANALYZE
SELECT name
FROM products
WHERE attributes @> '{"wireless": true}';
```

With only a few rows, PostgreSQL may use a sequential scan because scanning such a small table is inexpensive.

### Create the GIN Index

```sql
CREATE INDEX idx_products_attributes
ON products USING GIN (attributes);
```

### Query After Creating the Index

Run the same query again:

```sql
EXPLAIN ANALYZE
SELECT name
FROM products
WHERE attributes @> '{"wireless": true}';
```

The GIN index is designed to improve JSONB containment searches such as those using the `@>` operator.

For this experiment, the table contains only five products, so PostgreSQL may still choose a sequential scan even after the index is created. This is because using an index can have more overhead than scanning a very small table. On a much larger product table, the GIN index can significantly reduce the number of rows that PostgreSQL needs to examine.

Therefore, `EXPLAIN ANALYZE` is useful for comparing the execution plan and execution time before and after indexing.

### PostgreSQL JSONB vs MongoDB

PostgreSQL accesses JSONB values using operators such as `->>`, `@>`, and `?`, while MongoDB commonly accesses nested document fields using dot notation such as `"attributes.ram_gb"`.

MongoDB stores data naturally as documents, so working with highly flexible and nested data can be straightforward. PostgreSQL JSONB provides similar flexibility while also retaining relational features such as SQL joins, constraints, typed columns, and transactions.

Indexing also differs. PostgreSQL can use a GIN index on an entire JSONB column for several JSONB operations, whereas MongoDB allows indexes to be created directly on specific nested document fields.

For this product catalog, both databases can represent the data effectively. PostgreSQL is particularly useful when the product catalog is part of a larger relational system, while MongoDB provides a natural document-oriented approach when flexible documents are the main data model.
